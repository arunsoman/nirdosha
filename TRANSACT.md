# Nirdosha `transact` — durable, verified, compensating side effects

This is the Nirdosha-native answer to what Argus/Avalon/Atomos each built as
a whole distributed-OS-sized runtime (guardians, topactions, open nesting,
commit/abort handlers — see the design conversation this doc grew out of).
The finding that matters: none of that needs to become ten new keywords
here. Nirdosha's "external effect" already *is* a named function call
(`sandbox f(args)`, `connect(...)`, `tcp` send/recv) — so durable-transaction
support is a rollback-and-replay discipline layered over calls that already
exist, not a new subsystem. One keyword, six slots.

**Status: all five layers are implemented** (in-process control flow, a
real durability log, crash replay, `network`'s own `retry`/`timeout`, and a
real cross-process `network`/`commit` test) — see "How we're going to get
there" below for exactly what each one delivered.

## What it brings to the table

**1. Names the actual failure mode, instead of assuming "no exception ==
success."** A network call returning `200 OK` is not the same fact as "the
business operation actually happened" — that's exactly the gap that
motivated this whole design. `verify` is a mandatory slot, not optional: you
cannot write a `transact` that skips inspecting whether `network` really
succeeded.

**1b. The same rigor now applies to `commit`, not just `network`.**
Investigation while building the durability layer found that `commit`'s
return value was originally "unconstrained and discarded" — so a
`db_execute`-style failure inside `commit` (which returns a `Result`, never
traps) was invisible to `transact`: it still reported `true`. Fixed: a
`commit`/`compensate` call that traps, *or* whose declared return type is
`Result<T, E>` and comes back `Err`, is now treated as a failure and
retried — see "Runtime protocol" below.

**2. Crash-recoverability without a `guardian`/`stable` type-former.**
Argus needed `stable` vs. `volatile` fields as a language-visible
distinction because *any* guardian state could need to survive a crash.
Nirdosha only needs one thing to survive a crash: "did `network` already
run for this `transact`, and what did it return." That's narrow enough to
be an interpreter-owned runtime service (a real, synchronous, file-backed
SQLite log — `src/transact_log.rs`), invisible in syntax — the same way
`rand_seed` is a per-`Interpreter` field, not a language construct. Row 6
(goal.md) stays honored: a program that never uses `transact` never touches
the filesystem for this at all.

**3. Retry and timeout as "fundamentally expected," not bolted on later.**
A network call that can time out or transiently fail is the normal case,
not the exception — so `retry`/`timeout` are part of the `network` slot's
own grammar, not a separate wrapper the programmer has to remember.
`timeout` is real (a background-thread-plus-channel race against the
clock — this interpreter isn't `Sync`, so it can't preempt `self` directly;
see "Runtime protocol"), which is also why a new `sleep_ms(ms)` builtin
exists now: the one concrete way `.nir` source can simulate a slow/hanging
call to actually exercise `timeout` against, since nothing else in the
language could block on demand before.

**4. Reuses the existing affine-call discipline instead of inventing
first-class functions.** Every slot takes exactly one named `call` —
`Expr::Call`-only, same restriction `spawn call`/`sandbox call` already
enforce. This was a real fork (see the conversation this doc grew out of):
true first-class function values were the other option, and were rejected
as a much bigger structural addition to the language (a whole new type
category) for no semantic gain over named slots.

**5. Durability that doesn't overclaim.** No purely local mechanism —
logging, retries, replay — can make `network` itself exactly-once: a crash
mid-flight can't distinguish "request never sent" from "sent, response
lost." So `network`'s call is required to carry an idempotency key
(`txn_id`, generated by the runtime) precisely so a correctly-built
downstream can dedupe a replay-driven resend. This is a fundamental
distributed-systems limit, not a gap in this design, and it's the one place
`transact`'s guarantee genuinely depends on cooperation outside the
language — see "The recoverability boundary" below for the other, narrower,
honestly-named gap this surfaced (a crash that preempts `commit`/
`compensate`'s own argument logging).

## The construct, locked

```ebnf
stmt          ::= ... | transact_stmt

transact_stmt ::= "transact" "{"
                     ("precheck"  ":" call)?
                     "network"    ":" call ("retry" int_lit)? ("timeout" int_lit)?
                     "verify"     ":" call
                     "commit"     ":" call
                     ("compensate" ":" call)?
                     ("log"        ":" call)?
                   "}"
```

- Slot order is fixed (`precheck`, `network`, `verify`, `commit`, optional
  `compensate`, optional `log`) — no permutation parsing, keeps this LL(1)
  the same way every other fixed-arity form in this grammar already is.
  `retry N` (total attempts, `None`/absent means exactly one — TRANSACT.md's
  original "default 1, i.e. no retry") and `timeout N` (whole seconds, per
  attempt) both modify `network` only, parsed right after its own call.
- `precheck` (optional) runs first, before anything durable is written —
  must return `bool`; `false` aborts the whole block immediately, with
  nothing ever logged. The fix for "the DB was already down before
  `network` ran": a cheap, fast-failing check (e.g. a `db_ping()`-backed
  function) stops the block before any real-world side effect fires.
- `txn_id: str` is a third implicit local binding (alongside `network`/
  `verify`), generated by the interpreter the instant the block starts,
  before `precheck` even runs. `network`'s call **must** reference it in
  its own arguments — typeck-enforced (`TransactNetworkMustUseTxnId`).
- `network` and `verify` become implicit local bindings, typed exactly like
  a `let` would type them from the call's return type, visible to every
  slot after them (`verify: check(network)`, `log: write_log(amount,
  verify)`), scoped only inside the `transact` block.
- `verify`'s call must return `bool` — a new, specific `TypeErrorKind`
  (matching the precision of existing ones like `WrongIndexArity`,
  `SingularMatrix`), not a generic type mismatch.
- **`verify`'s arguments are restricted to exactly `network`/`txn_id`** —
  never an outer-scope variable from the enclosing function
  (`TransactVerifyArgsMustBeImplicitBindings`). This is what makes crash
  replay from the narrowest possible crash window (during/right after
  `network`, before `verify` ever ran in the original process) fully
  sound: `network`'s result and `txn_id` are always known to
  `replay_pending_transactions`, so `verify`'s exact original call can
  always be rebuilt. Matches `verify`'s own contract anyway — "inspect
  `network`'s outcome," nothing more — and every worked example already
  satisfies it.
- **Every value that crosses the durability boundary must be a plain
  scalar** (`i*`/`u*`/`usize`/`f64`/`bool`/`str` — `Ty::is_transact_scalar`;
  no `db`/`tcp`/`thread`/`sandbox` handle, no aggregate/struct/enum).
  Applies to every argument of `network`/`verify`/`commit`/`compensate`,
  and to `network`'s own declared return type (`TransactValueNotDurable`)
  — the log has to be able to serialize and replay these values after a
  crash, and a live resource handle can't survive a process restart.
  `precheck`/`log`'s arguments are unconstrained — neither is ever logged
  or replayed.
- `transact { ... }` is itself a value: `true` if it committed, `false` if
  it compensated (or if there was no `compensate` slot and `verify` was
  `false`, or if `precheck` returned `false`) — same block-value
  convention `if` already uses. If `commit`/`compensate`'s retry budget is
  exhausted, `transact` **traps** instead — see "Runtime protocol."
- `timeout N` is whole seconds, plain `int_lit`, no unit suffix — no new
  duration-literal lexer syntax invented here on purpose (see Decisions).

```nir
fn db_reachable() -> bool { ... }                        // precheck
fn call_api(txn_id: str, amount: i64) -> i64 { ... }     // network
fn check(resp: i64) -> bool { ... }                      // verify
fn update_db(amount: i64) -> i64 { ... }                 // commit
fn refund(amount: i64) -> i64 { ... }                    // compensate
fn write_log(amount: i64, ok: bool) -> unit { ... }

fn checkout(amount: i64) -> bool {
    return transact {
        precheck:   db_reachable()
        network:    call_api(txn_id, amount) retry 3 timeout 5
        verify:     check(network)
        commit:     update_db(amount)
        compensate: refund(amount)
        log:        write_log(amount, verify)
    }
}
```

## Runtime protocol

1. `txn_id` is generated. `precheck` (if present) runs; `false` aborts
   here, nothing durable is ever written.
2. Before `network` runs, the interpreter durably appends a pending record
   `{txn_id, network's callee+args, verify/commit/compensate's callee
   names}` to the log (all four callee *names* are static, known up
   front; only arguments are dynamic and logged as each slot is reached).
3. `network`'s call runs, retried up to `retry` times (default 1) on
   failure — a trap, or a `timeout`-second deadline elapsing first, both
   count as a failed attempt; `verify == false` is never a retry
   condition (`verify` hasn't even run yet at this point). No backoff
   between attempts — re-invokes the exact same call expression with the
   same already-evaluated arguments, per this section's original design.
   Its result is appended to the log **before** `verify` runs — this is
   the actual crash-safety boundary: a restart that finds "network ran,
   result X, no terminal marker" resumes at step 4, never re-invoking
   `network`.
4. `verify(network)` runs.
5. `verify == true` → `commit` runs, retried with bounded exponential
   backoff if it fails (a trap, or a `Result<T, E>` return in its `Err`
   variant — see "What it brings to the table" §1b). Success appends a
   terminal `committed` marker, then `log` runs (best-effort only — a
   trap inside `log` is swallowed, never undoes an already-successful
   `commit`/`compensate`; never itself logged to the durability log,
   never replayed). If the retry budget is exhausted, `transact` **traps**
   (`TransactCommitPending`) rather than guessing — the record stays
   `commit_pending`, and a restart (or the same reconciliation run again
   later) keeps retrying it independently of whatever the trap's caller
   did.
6. `verify == false` → `compensate` runs if present, same retry-and-trap
   treatment as `commit` (`TransactCompensatePending` on exhaustion), then
   a terminal `compensated` marker, then `log`. No `compensate` slot at
   all is immediately terminal.

**`compensate` is never triggered by a `commit` failure** — only by
`verify == false`, a deliberate business rejection. Auto-reversing a
real, already-`network`-succeeded effect (a refund, a cancelled order)
because a local write hit a transient infra fault would itself be a
partial-failure-shaped bug, arguably worse than the one this feature
exists to prevent — see the design conversation this doc grew out of for
why "DB down before `network`" and "DB down after `network` succeeds"
are handled identically by retry-until-success rather than special-cased.

If `network` still traps (or times out) after its `retry` attempts are
exhausted, the whole `transact` block traps and propagates — there is
nothing to compensate, since `network` never returned a result to act on.
A timeout reports the specific `TransactNetworkTimedOut { seconds }`, not
a generic error. The record stays `pending`, exactly what crash replay
resumes from — and resumes with the *same* `retry`/`timeout` budget the
original live attempt had (captured durably at step 2, alongside the
other callee names), so a `network` written to legitimately hang can't
also hang startup replay itself indefinitely.

### `timeout`'s actual mechanism — an honest, bounded escape hatch

This interpreter is not `Sync` (`rng`'s `RefCell`, `call_depth`'s `Cell`),
so a timed call can't run `self` on another thread the way a true
preemptive timeout would. Instead it's exactly the pattern `Expr::Spawn`
already uses: a brand-new `Interpreter` sharing only cheap `Arc` clones of
the immutable program/source/tracer, sends its result over a channel; a
`recv_timeout` past the deadline gives up waiting and reports the timeout
— but the spawned thread itself is **not** killed (Rust has no such
mechanism). Like `SANDBOXING.md`'s `recv`, it keeps running in the
background and its eventual result, if any, is simply discarded. This is
an honest, named limit, not a claim of true preemption.

## Crash replay (`Interpreter::replay_pending_transactions`)

Called once at process startup (`main.rs`'s `run`/`serve` commands do this
before ever calling `main`/serving a request), scans every non-terminal
row and resumes it:

- `commit_pending` / `compensate_pending` — fully resumable: the callee
  and its exact evaluated arguments were durably captured before the
  crash, so this is just the retry-with-backoff loop again.
- `pending` / `network_done` — `network`'s result (re-confirmed via the
  same `txn_id` if still `pending`) and `verify`'s arguments (always
  reconstructable, per the `network`/`txn_id`-only restriction above) are
  never a problem.

### The recoverability boundary — one honest, named gap

`commit`/`compensate`'s own arguments can legitimately reference
outer-scope variables from the enclosing function call (an `amount`
parameter, say) that crashed away with the original process and were
never durably captured — that only happens once the live run actually
reached `mark_commit_pending`/`mark_compensate_pending`. If replay
determines a write is needed but those arguments were never logged, the
row is reported `Stuck`, not guessed at: this needs the original request's
context back (a human, or the caller reissuing the same operation through
a legitimate new path), not more cleverness in the replay code. This is
the honest price of `commit`/`compensate` being allowed to close over
arbitrary business data (unlike `verify`, which is restricted precisely to
avoid this) — deliberately not "solved" by also restricting `commit`'s
arguments, which would break the entire point of `commit` (it's supposed
to finish the business operation, not just re-inspect `network`).

**2026-08-26 — a real, narrower sub-case of this gap found and closed**
(`ROADMAP.md` Track A1's real-process-kill test, `tests/
transact_process_kill.rs`): a crash landing in the short window *between*
`record_verify` and `mark_commit_pending` (verify already succeeded, but
`commit`'s arguments hadn't been durably captured yet) used to be an
unconditional `Stuck` even when `commit`'s arguments happened to be
exactly `network`/`txn_id` — the same always-safe shape `verify`'s own
arguments are statically restricted to, and the shape every worked example
in this file already uses (`update_db(network)`, `refund(amount)`'s
`amount` being `network`, etc.). A real `nirdosha serve` process, SIGKILLed
under real concurrent HTTP load (not the in-process simulation `tests/
transact_durability.rs` already had), hit this exact row shape on the first
try. Fixed: `commit`/`compensate`'s arguments are now also classified
per-argument at `begin_pending` time (`commit_arg_kinds`/
`compensate_arg_kinds` — `"network"`, `"txn_id"`, or `"opaque"` for
anything else), the same static-but-optional bookkeeping `verify_arg_kinds`
already does, just without `verify`'s compile-time guarantee that every
argument qualifies. `Interpreter::replay_one` now reconstructs `commit`/
`compensate`'s arguments from this classification (mirroring how it
already reconstructs `verify_args`) whenever the durably-captured
`commit_args`/`compensate_args` are missing — falling back to `Stuck` only
when at least one argument is genuinely `"opaque"` (a real outer-scope
reference), which is exactly the gap this section describes and is still,
correctly, unclosed. `TransactLog::open` backfills the two new columns via
`ALTER TABLE` for a pre-existing log file (defaulted to always-`"opaque"`,
i.e. exactly the old, safe-but-`Stuck` behavior for whatever a pre-upgrade
row already had logged) — a durability log has to survive a binary
upgrade across a real restart, not just a fresh file. See `tests/
transact_durability.rs`'s `replay_reconstructs_commit_args_from_network_
and_txn_id_when_the_crash_landed_after_verify_but_before_mark_commit_
pending` (and its `compensate` sibling) for the in-process reproduction,
and the negative control (`replay_resumes_network_from_pending_but_
reports_stuck_when_commit_args_were_never_captured`, unchanged) for
confirmation the genuine outer-scope-reference gap is still honestly
`Stuck`, not silently papered over.

## How we're going to get there — layers, not a syntax spec

Same discipline `SANDBOXING.md` already committed to: each layer ships,
gets its own tests and example, before the next starts. The full design
above is locked as the *target*.

1. **`transact` in-process, no durability, no retry/timeout.** ✅ Done.
   Parser, typeck (implicit `network`/`verify` bindings, the `bool`-return
   check on `verify`), ownership (slots are ordinary calls — nothing new
   for `ownership.rs` to reason about), interpreter execution of the
   protocol.
2. **`retry`/`timeout` on `network`.** ✅ Done —
   `Interpreter::call_network_with_retry`/`call_with_timeout`
   (`interpreter.rs`). A real wall-clock read and a real background
   thread for the timeout — an explicit, called-out departure from the
   determinism story (`goal.md`'s determinism section only covers
   `rand_seed`'s RNG stream; this is new, unavoidable nondeterminism, same
   honesty `SANDBOXING.md` already gives "`recv` can block forever"), and
   the reason a new `sleep_ms` builtin exists — see "`timeout`'s actual
   mechanism" above for exactly how, given this interpreter isn't `Sync`.
   Retry re-invokes the exact same call expression with the same
   evaluated arguments; a trap (or a timeout) is the only thing "retry"
   reacts to — `verify` returning `false` is not a retry condition, it's
   the compensate path. The budget is also captured durably, so crash
   replay's own `network` re-invocation from a `"pending"` row honors it
   too, not just the live path.
3. **The durability log itself.** ✅ Done — `src/transact_log.rs`, a real,
   synchronous, file-backed SQLite log (`PRAGMA synchronous = FULL`),
   owned by the `Interpreter` (`Option`-free: a program using `transact`
   can't forget to turn it on, no flag to omit — only *where* it lives is
   configurable, via `--transact-log <path>` or `Interpreter::
   with_transact_log_path`). Also added along the way, once the durability
   log made the gap concrete: the `precheck` slot, the mandatory `txn_id`
   idempotency key, the durable-scalar restriction on everything that
   crosses the boundary, and `commit`/`compensate`'s retry-and-trap
   treatment (§1b above).
4. **Crash replay.** ✅ Done — `Interpreter::replay_pending_transactions`,
   called at `main.rs`'s `run`/`serve` startup. See "Crash replay" above
   for the exact recoverability boundary.
5. **Cross-process `network`/`commit`.** ✅ Done (tested) for `connect`/
   `tcp` — `tests/transact_durability.rs`'s
   `network_slot_talks_to_a_real_separate_process_over_tcp`: `network`'s
   function opens a real TCP connection, sends `txn_id`, reads a reply,
   all inside a `transact { ... retry 3 timeout 5 }` block, proving the
   whole durability/retry/timeout protocol against a real socket, not
   just a local pure function — no grammar change needed, confirming the
   original "one named `Expr::Call`, unconstrained body" bet.
   `examples/transact_cross_process.nir` is the illustrative,
   real-external-listener-required demo (the same split `tests/tcp.rs`
   already has with `examples/tcp_client.nir`). `sandbox`/`db_connect`
   remain equally legal via the identical mechanism but aren't separately
   tested — the TCP case already exercises the load-bearing property
   (`network`'s body doing real I/O across a socket boundary).

## Decisions

Resolved now rather than left open, matching `SANDBOXING.md`'s own
practice:

- **Slot operand is exactly `Expr::Call`, never a bare `sandbox`/`connect`
  expression directly.** Keeps `transact`'s own grammar simple and
  consistent with `spawn`/`sandbox`'s existing restriction; a slot that
  needs a real network/process effect wraps it in a named function, which
  every worked example above already does.
- **Retry only reacts to a trap, never to `verify == false`.** Conflating
  "the call itself failed" with "the call succeeded but the business
  outcome was negative" is exactly the bug this whole feature exists to
  prevent — collapsing them back together in the retry logic would
  reintroduce it one layer down.
- **`commit`'s and `compensate`'s return types are unconstrained** except
  for the failure-detection rule in §1b (a trap, or `Result<T, E>`'s
  `Err`, is a failure to retry) — everything else about the return value
  is still discarded, same treatment `expr_stmt` already gives a bare
  expression statement. `log`'s return type is fully unconstrained, no
  exception.
- **No duration-literal syntax (`5s`) invented for `timeout`** — plain
  `int_lit` seconds. A real duration literal is future work if/when it's
  needed elsewhere too, not a one-off invented here.
- **Durability is an interpreter-owned runtime service, not a `stable`/
  `guardian` type-former.** Narrower surface, zero new type-checking
  machinery, and it's the only thing Nirdosha's version of "guardian
  state" actually needs (whether `network` already ran, and now also
  whether `commit`/`compensate` did) — unlike Argus, which needed the
  distinction on arbitrary user fields.
- **`verify`'s arguments are statically restricted to `network`/`txn_id`,
  but `commit`/`compensate`'s are not.** A real, deliberate asymmetry:
  `verify`'s whole contract is "inspect `network`'s outcome," so
  restricting it costs nothing and buys full crash-replay soundness for
  the narrowest window; `commit`/`compensate` are supposed to close over
  arbitrary business data to actually finish the operation, so the same
  restriction there would defeat their purpose. The honest cost of that
  asymmetry is "Crash replay"'s named `Stuck` gap above.
- **Compiled backend (`codegen.rs`) is out of scope until the interpreter
  version is proven** — same "reject, don't mis-compile" treatment every
  other unimplemented construct gets today (`thread`, `chan`, `sandbox`,
  `struct`/`enum`/`match`, `db`/`mq`/`json` are still interpreter-only
  per `LANGUAGE.md` §10 — `box`/`tcp` compile now, so they've dropped off
  that list; `transact` joins the still-unsupported one, not an
  exception to it).
